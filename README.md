# UZ Tickets Telegram Bot

Інтерактивний Telegram-бот, який дозволяє обрати маршрут прямо в чаті
(дати → звідки → куди → пересадки чи ні), і раз на 15 хв перевіряє
наявність квитків, надсилаючи сповіщення, коли рейс **вперше** стає
доступним (не на кожну зміну кількості місць — щоб не спамити).

**Мультикористувацький**: будь-хто, хто напише боту, керує СВОЇМИ
обраними маршрутами незалежно від інших — маршрути й сповіщення
прив'язані до `chat_id` кожного користувача.

## Як це працює всередині

Дані тягнуться з внутрішнього API `app.uz.gov.ua` (не з
`booking.uz.gov.ua` напряму — той сам по собі SPA-обгортка без даних):

- `GET app.uz.gov.ua/api/v3/trips?station_from_id=...&station_to_id=...&with_transfers=0|1&date=YYYY-MM-DD`
  — прямі рейси (`direct`) і, за бажанням, рейси з пересадкою
  (`with_transfer`, кожен елемент — список "ніг" маршруту).
- `GET app.uz.gov.ua/api/stations?query=...` — пошук станції за назвою.

Обидва підтверджені реальними відповідями сервера. `uz_client.py`
відтворює ці запити через `curl_cffi` (щоб TLS-відбиток виглядав як у
справжнього браузера — сам `booking.uz.gov.ua` раніше блокував "голий"
`requests` саме за цим критерієм).

Один спільний `UZClient` (одна гостьова сесія) використовується для
всіх користувачів бота — конкурентні запити серіалізуються через
`asyncio.Lock` (curl_cffi `Session` не гарантовано безпечна для
одночасних запитів з різних потоків).

## Встановлення

```bash
python -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

Заповніть `.env`:
- `TELEGRAM_BOT_TOKEN` — отримати у [@BotFather](https://t.me/BotFather)
- `POLL_INTERVAL_SEC` — інтервал фонової перевірки, за замовчуванням 900
  (15 хв)

`TELEGRAM_CHAT_ID` більше не потрібен — бот мультикористувацький,
сповіщення йдуть тому, хто додав маршрут.

## Запуск

```bash
python bot.py
```

Будь-хто пише боту `/start` — з'являється меню:

- **🔍 Обрати новий рейс** — покроковий діалог: спершу режим дати
  ("Одна дата" / "Проміжок дат"), тоді інлайн-календар → станція
  відправлення → станція призначення → враховувати пересадки чи ні.
  Доступно, лише якщо у ЦЬОГО користувача ще немає активного маршруту.
- **⚙️ Налаштування та обрані рейси** — список ЙОГО обраних маршрутів
  із номерами (#1, #2, ...) і кнопка "🗑 Скинути" на кожен.

## Файли

- `bot.py` — точка входу: меню, діалог вибору маршруту, фоновий цикл.
- `storage.py` — збереження обраних маршрутів (`selected_routes.json`),
  прив'язка до `chat_id`, наскрізна нумерація (ніколи не повторюється).
- `uz_client.py` — HTTP-клієнт до app.uz.gov.ua.
- `state.py` — дедублікація сповіщень (`state.json`).
- `formatting.py` — форматування тексту сповіщення.
- `test_app_api.py`, `test_stations_search.py`, `test_with_transfers.py` —
  самодостатні скрипти для швидкої перевірки ендпоінтів окремо від бота.

**Застаріле** (з часів статичного конфіга до появи інтерактивного бота,
залишені для довідки, більше не використовуються): `main.py`,
`routes.py`, `notifier.py`, `stations.py`.

## Розгортання (щоб бот працював 24/7)

Боту треба постійно "слухати" Telegram (`run_polling()`) — це процес,
який має бути живим весь час, а не короткочасна задача за розкладом.

**GitHub Actions тут НЕ підходить**: джоби виконуються і завершуються,
а не висять вічно; навіть `schedule: cron` не гарантує точний час
(затримки в 10-30+ хв не рідкість на безкоштовному плані); а
ефемерні runner-и означають, що `selected_routes.json`/`state.json`
довелось би зберігати десь окремо. Actions підійшов би хіба для самої
фонової перевірки без меню, але тоді довелось би тримати дві різні
частини системи в різних місцях — зайва складність.

Варіанти, що дійсно підходять:

1. **Власний ПК/сервер** (як зараз) — найпростіше, нуль тертя:
   - Linux: `systemd`-юніт із `Restart=always`, або `tmux`/`screen` +
     `nohup python bot.py &`.
   - Windows: Task Scheduler з "Run at startup", або залишити
     консоль відкритою.

2. **Oracle Cloud Always Free Tier** — реально безкоштовна VM
   (ARM Ampere A1, до 4 OCPU/24 GB, назавжди, не пробний період).
   Найкращий безкоштовний варіант для процесу 24/7, але є тертя:
   потрібна кредитна картка при реєстрації (верифікація, не
   списання), і в деяких регіонах трапляються проблеми з
   доступністю ARM-інстансів ("out of capacity" — тоді просто
   пробуєте інший регіон). На отриманій VM — той самий підхід із
   `systemd`, що й для власного сервера.

3. **Дешевий VPS** (~$3-5/міс, напр. Hetzner) — якщо тертя з Oracle
   набридне. `Fly.io`, до речі, більше не має безкоштовного тарифу
   для нових акаунтів (прибрали в 2024) — не варто орієнтуватись на
   нього.

## Швидкий тест окремих ендпоінтів

Не обов'язково запускати весь бот, щоб перевірити щось окремо:
```bash
python test_app_api.py           # пряма перевірка /api/v3/trips
python test_stations_search.py   # перебір варіантів пошуку станції
python test_with_transfers.py    # структура рейсів із пересадкою
```

## Мультикористувацький режим

Бот тепер працює для будь-кого, хто йому напише — кожен `chat_id` керує
своїми маршрутами незалежно. `selected_routes.json` зберігає маршрути під
кожним `chat_id` окремо; `state.json` (дедублікація сповіщень) лишається
спільним файлом, але конфліктів немає — номер маршруту (`route{id}`) у
ключі глобально унікальний (наскрізний лічильник `next_id`, спільний на
всіх користувачів, ніколи не повторюється).

Обмеження UI лишається: **один активний маршрут на користувача** —
кнопка "Обрати новий рейс" пропонує спершу скинути наявний, якщо він уже
є САМЕ У ЦЬОГО chat_id.

## GitHub Actions (поки що для тестування)

**Персональні дані користувачів (`chat_id`, реальні маршрути) — у
`selected_routes.json`/`state.json`.** Публічний git-репозиторій означає,
що вся історія коммітів видна всім назавжди (навіть після видалення
файлу пізнішим коммітом), а логи запусків Actions для публічних репо
теж публічні. Два варіанти, як з цим бути:

### Варіант A — приватний репозиторій (найпростіше)

GitHub → Settings → General → Danger Zone → Change visibility → Private.
Закриває обидва канали одразу, без додаткового коду. Мінус — безкоштовний
ліміт хвилин Actions менший (2000 хв/міс), і `*/15 * * * *` (≈2880 хв/міс)
трохи вилазить за нього — див. нижче.

### Варіант B — публічний репозиторій + шифрування даних

Якщо хочете лишити код відкритим (наприклад, ділитись/показувати
портфоліо), `crypto_store.py` шифрує `selected_routes.json`/`state.json`
симетричним ключем (`Fernet` — AES128-CBC + HMAC) через `ENCRYPTION_KEY`,
який лишається лише в GitHub Secrets і локальному `.env` — НІКОЛИ не в
git. Без ключа закомічені файли — нечитабельний шифротекст.

Додатково прибрав `chat_id` з усіх `logger.*` викликів і з повідомлень
git-коммітів (`_git_sync` у `storage.py`) — там тепер лише внутрішній
номер маршруту (`route{id}`), який без розшифрованого файлу нічого не
каже про те, хто саме за ним стоїть.

Налаштування:
1. Згенеруйте ключ:
   ```bash
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```
2. Той самий ключ — і в GitHub Secrets (`ENCRYPTION_KEY`), і в
   локальному `.env` (`bot.py`, коли робить `git_sync`, теж має шифрувати
   тим самим ключем, інакше зашифроване локально й розшифроване в Actions
   не збіжаться).
3. **Важливо**: якщо ключі розійдуться (різні значення локально й у
   secrets) — це НЕ впаде з чіткою помилкою. `Fernet`-шифротекст сам по
   собі виглядає як valid UTF-8 (base64), тож розшифровка з неправильним
   ключем тихо провалиться, і код інтерпретує це як "файл пошкоджений
   /порожній" — тобто просто побачите порожній список маршрутів замість
   зрозумілої помилки. Якщо після налаштування раптом "усі маршрути
   зникли" — перше, що перевірити.

**Публічний репозиторій ≠ нульовий залишковий ризик**, навіть із
шифруванням: сама наявність активності (коли саме відбуваються
коміти/запуски) технічно видима. Для цього проєкту це прийнятно —
йдеться про захист вмісту (хто/куди їде), а не про приховування самого
факту використання бота.

### Бюджет хвилин Actions

Приватні репо на безкоштовному плані GitHub дають 2000 хв/міс (публічні —
без обмежень). Прогін кожні 15 хв = 96 разів/день ≈ 2880 хв/міс (GitHub
рахує мінімум 1 хв за запуск, навіть якщо скрипт відпрацював за 20 сек) —
трохи більше за безкоштовний ліміт для приватного репо. Варіанти: (a)
прийняти можливе невелике списання (переліміт ≈$0.008/хв на
Linux-раннерах — орієнтовно $5-7/міс, і лише якщо прив'язана платіжна
картка — інакше GitHub просто зупинить workflow до наступного місяця),
або (b) поставити інтервал трохи довшим (`cron: '*/20 * * * *'` ≈2160
хв/міс, чи `*/30 * * * *` ≈1440 хв/міс — впевнено в межах ліміту). Для
публічного репо цей пункт неактуальний.

`check_once.py` — окремий одноразовий скрипт (не `bot.py`): без меню,
просто одна перевірка всіх обраних маршрутів усіх користувачів + надсилання
сповіщень. Саме його запускає `.github/workflows/check-tickets.yml`.

**Важливо розуміти, що це НЕ повноцінна заміна `bot.py`:**
- Немає інтерактивного меню — обирати маршрут через GitHub Actions
  неможливо (Actions не "слухає" Telegram у реальному часі). Маршрути
  досі додаються через живий `bot.py` (локально/на сервері), а
  `selected_routes.json` з результатом треба закомітити в репозиторій
  вручну (або придумати автоматичну синхронізацію — поки не зроблено).
- Runner GitHub — одноразова машина, тож `state.json` (дедублікація)
  зберігається між запусками ЛИШЕ тому, що workflow сам комітить його
  назад у git після кожного прогону (крок "Commit updated dedup state").
  Без цього кроку кожен запуск вважав би все "новим".
- `cron` у GitHub Actions — орієнтовний, не точний. На безкоштовному
  плані реальні затримки в 10-30+ хв — не рідкість, особливо в пікові
  години.
- **Ризик з IP**: GitHub-раннери — датацентрові IP (Azure), а вся наша
  робота з `curl_cffi`/`IMPERSONATE_PROFILES` була про те, щоб пройти
  бот-детект booking.uz.gov.ua з ЗВИЧАЙНОЇ (домашньої) адреси. Немає
  гарантії, що те, що працює з домашнього ПК, так само пройде з
  датацентрового IP — можливо, доведеться дивитись у логи `ensure_connectivity`.

### Налаштування

1. Створіть репозиторій на GitHub, закомітьте туди весь цей код.
2. Settings → Secrets and variables → Actions → додайте секрет
   `TELEGRAM_BOT_TOKEN`.
3. Локально запустіть `bot.py`, додайте через меню тестовий маршрут —
   з'явиться `selected_routes.json`. Закомітьте цей файл у репозиторій
   (для першого тесту — вручну).
4. Actions → "Check UZ tickets" → Run workflow (ручний запуск,
   `workflow_dispatch`) — не чекайте на cron, перевірте одразу.
5. Погляньте логи кроку "Run check" — чи пройшло з'єднання, чи знайдено
   трипи, чи полетіло сповіщення в Telegram.

Якщо на кроці `ensure_connectivity` побачите, що жоден `impersonate`-профіль
не проходить — це, ймовірно, саме той ризик з датацентровим IP вище.

### Сценарій "додав маршрут — вимкнув сервер — далі сам GitHub"

Це і є та причина, заради якої варто ганяти `bot.py` не постійно, а лише
коли щось міняєте:

1. Клонуйте свій GitHub-репозиторій (не просто копію файлів — саме
   `git clone`, з налаштованим push-доступом: PAT у URL/credential
   helper, або SSH-ключ).
2. У `.env` цього клону виставте `GIT_SYNC=1`. Якщо йдете шляхом
   "публічний репо + шифрування" (Варіант B вище) — тут-таки виставте
   й той самий `ENCRYPTION_KEY`, що і в GitHub Secrets, інакше
   локальний коміт зашифрується іншим ключем, ніж очікує workflow.
3. Запустіть `python bot.py`, додайте (чи скиньте) маршрут через меню в
   Telegram — після кожної такої дії `storage.py` сам зробить
   `git add / commit / pull --rebase / push` для `selected_routes.json`.
4. Зупиніть `bot.py` (`Ctrl+C`), вимкніть комп'ютер — не важливо.
5. `check-tickets.yml` на GitHub Actions і далі йде за розкладом,
   бачить свіжий `selected_routes.json` із кожним новим коммітом,
   перевіряє й шле сповіщення, комітить назад `state.json`.
6. Захочете додати/скинути ще один маршрут — знову коротко запустіть
   `bot.py`, зробіть зміну, вимкніть.

Нюанси, про які варто знати:
- **Push може конфліктувати** з коммітами, які сам workflow робить у
  `state.json`. `_git_sync` у `storage.py` робить `git pull --rebase`
  перед push і просто логує помилку, якщо конфлікт — маршрут при цьому
  вже збережений ЛОКАЛЬНО, просто не запушений, доведеться розібратись
  вручну (`git status`, за потреби `git rebase --abort`).
- Якщо `git` не налаштований (немає push-доступу, чи `GIT_SYNC` не
  виставлено) — `add_route`/`remove_route` все одно працюють, просто
  без синхронізації; побачите про це попередження в логах бота.
- Меню в Telegram і без цього продовжує показувати актуальні дані з
  локального файлу — синхронізація односторонньо йде В GitHub, не назад.

Автоматичну покупку свідомо не включив — це вже інша категорія ризику
(реальні платежі, персональні дані пасажирів, суворіші вимоги до
надійності). Коли поточний функціонал стабільно попрацює — можна
окремо обговорити модуль бронювання/оплати.
